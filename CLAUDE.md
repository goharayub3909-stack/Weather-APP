# WeatherWalay Kissan & Sehat Hub

Static website deployed to GitHub Pages from `public/` whenever `main` changes.
Local dev server: `server.js` (Node 22+).

## Commands
- `npm start` runs the site at http://localhost:3000
- `npm test` runs the whole suite; they must stay green
- `npm run build:css` rebuilds `public/tailwind.css` after changing Tailwind
  classes in `public/index.html` or `public/farm-workspace.js`

## Rules
- Work on a branch and open a pull request. Merging to `main` publishes the live site.
- `pages.yml` rebuilds the site and its data files on a nominal 30-minute schedule, but GitHub throttles
  scheduled runs to every 3-6 hours in practice, and the data files are generated during the build,
  not committed. `observations.yml` refreshes only `stations.json` and `metar.json` about every 10 minutes
  (it queues its own next run) and publishes them to the `data` branch; `public/observation-feed.js` reads
  that copy and the deployed copy and keeps the newer. Freshness windows: stations 3 h, airports 2 h.
  Run `git pull` before starting work.
- New `.js`/`.css`/`.json` files must be added to the allow-list in `server.js`,
  or the app fails to start locally (the live site is unaffected).
- A 500 for `station-history/index.json` on localhost is expected.
- Never invent agronomy thresholds. Keep the "weather screen only, not a diagnosis"
  wording. Every index formula needs a numeric test in `test/farm-monitoring.test.js`.
- The imagery service (Microsoft Planetary Computer) rate-limits bursts with HTTP 429
  without CORS headers, so the browser sees a network error. Retry with backoff
  (`fetchRetry` in `public/farm-satellite.js`).

## Views
- The site has six separate views, one visible at a time, chosen by the URL hash: `weather-view`
  (`#overview`, `#hourly`, `#details`), `maps-view` (`#maps`), `health-view` (`#health`),
  `climate-view` (`#climate`), `flood-view` (`#flood`) and `farmers-view` (`#farmers`). The table lives in `public/views.js`;
  `navigate()` in `public/farmers.js` applies it and fires `viewchange` (and `farmviewchange` for Farmers).
- A new section goes inside one of those containers in `public/index.html`. Code that must pause when its
  page is hidden should check its own view container (see `maps.js`, `lightning.js`), not `weather-view`.
- The Weather-page restyle in `style.css` is scoped to `:is(#weather-view, #maps-view)`.

## Farmers section
- `public/farm-workspace.js`: full-screen map workspace (ticker, layer card,
  triage + decisions sidebar, bottom sheet). It MOVES existing panels, so element
  ids must not change. Tailwind is scoped to `#fw-root` with preflight off.
- `public/farm-satellite.js`: Sentinel-2/Landsat layers, 12-month whole-field report,
  timeline, boundary drawing and editing.
- `public/farm-indices.js`: index formulas (NDVI, EVI, EVI2, NDWI, NRI, DSWI, MSAVI,
  SAVI, NDRE, NDMI, LST, SMI), false colour, field-relative colour stretch.
- `public/field-operations.js`: spray/fertilise/harvest windows. `sprayChecks` is the
  single spray rule shared by the work calendar and the weather ticker.
- `public/disease-panel.js` + `disease-risk.js`: pest/disease risk; publishes the
  `farm-disease-results` event used by the triage feed.

## Climate section (main dashboard, `#climate`)
- `public/climate-hazards.js`: pure logic. IMD heat-wave / warm-night / cold-wave criteria, IMD 24 h rain
  classes, ETCCDI indices, ERA5 daily normals (1991-2020), two-day persistence, map grid. All thresholds
  live in the `IMD` and `ETCCDI` constants with their source; do not edit them without a source.
- `public/climate-era5.js`: free ERA5 via Open-Meteo archive (one request 1991 to latest, map grid in
  chunks, 429 retry with backoff), ECMWF forecast, station reads.
- `public/climate-panel.js`: day / month / year ERA5 map, hazard cards (past ERA5, nearest station,
  next 7 days ECMWF), forecast table, history charts. Tailwind scope includes `#climate`.
- Cold-day criteria are deliberately not assessed (official definition not confirmed). IMD criteria are
  Indian, not PMD warnings: keep the screening-only wording.

## FloodAI section (main dashboard, `#flood`)
- `public/flood-logic.js`: pure logic. SCS curve numbers (USDA TR-55) and antecedent-moisture adjustment, Manning n
  (Chow 1959), Gumbel return periods from ERA5 annual maxima, return-period risk bands, gauge correction, Kirpich +
  SCS unit hydrograph, CSV parsers. Every constant names its source; rows marked `assumed` have none. Do not
  change them without a source.
- `public/flood-terrain.js`: AWS Terrain Tiles (Terrarium) decode, Web-Mercator maths, D8 flow, accumulation,
  Strahler order, catchment, profiles. `public/flood-model.js`: 2D local-inertial rain-on-grid solver (mass is
  tested). `public/flood-data.js`: ECMWF-only hourly rain, WeatherWalay gauges, tiles, OSM buildings.
  `public/flood-chart.js` / `flood-panel.js`: interactive SVG charts and the UI. Tailwind scope includes `#flood`.
- `public/flood-eo.js` (pure, tested) + `flood-eo-panel.js` (UI): ESA WorldCover per-pixel cover and curve numbers,
  Sentinel-1 water (Planetary Computer item tiles of `10*log10(vv_b1)`, one orbit, monthly scenes, Otsu threshold, 3x3
  despeckle, slope mask), channel / banks / thalweg, observed floods and model skill (POD, FAR, CSI), flooded cropland,
  people lower bound (OSM homes x 6.3), and the 3D view (MapLibre in `public/vendor/`, loaded on demand). In 3D use
  GeoJSON polygons for flood layers: MapLibre image sources render black over terrain.
- Rain is ECMWF only. Gauge correction uses fresh WeatherWalay stations (PMD gauges use a different day window).
  Screening only: keep the "not an official flood forecast or warning" wording. Not built: upstream inflow, a soil map,
  WorldPop population (no CORS), LiDAR (none is free for Pakistan; users import sections).

## Maps page: 3D terrain explorer (`#maps`, "Wind & weather" tab)
- `public/explorer/` replaces the old OpenLayers studio (it is still an iframe from `index.html`, and still honours the `badal-studio-visibility` message). `core.js` is pure and tested (`test/terrain-explorer.test.js`); `app.js` is three.js (vendored in `public/vendor/three/`).
- Data, best first: `scripts/sync-terrain-weather-ecmwf.py` reads ECMWF's own free open data (IFS 0.1 degree, about 9 km, CC BY 4.0, no key, no API limit; mirrors on Google, AWS and data.ecmwf.int) by byte range, decodes it with eccodes and writes `public/terrain-data/grid-hires.json` (3-hourly, 72 h, packed Int16 as base64, about 27 MB, schema 2). Surface fields: 10 m wind, 2 m temperature (`t2m`), cloud, total precipitation, snowfall, most-unstable CAPE (`cape`); pressure-level winds `u850 v850 u700 v700`. It also caches `mx2t3`, `mn2t3` and `ssrd` for the 1 km downscaler (not written to the grid) and then runs `downscaler/2_apply_1km_forecast.py` (skip with `--no-downscale`; see "1 km downscaler" below). A level is set to missing wherever the surface pressure says it is below the ground (the model extrapolates under terrain). Needs `pip install eccodes numpy` (locally the permanent `.venv-terrain`: `.venv-terrain/Scripts/python.exe scripts/sync-terrain-weather-ecmwf.py [--force] [--workers N]`; the build installs them). One run downloads about 1 GB by parallel byte ranges (16 workers, about 4 minutes here) and caches decoded fields in `%TEMP%/weatherwalay-ecmwf-cache/<run>`, so a rerun of the same run takes seconds. Fallback: `scripts/sync-terrain-weather.mjs` (Open-Meteo, 0.5 degree, no temperature or levels). Both files are generated, never committed; the page loads the 0.1 degree file first. Fields added later (`PACKED_OPTIONAL` in `core.js`) are optional, so an older grid still loads and the matching controls are disabled.
- Packing rule (a real bug, fixed): in `pack()` clip BEFORE writing the missing marker. -32768 is reserved for "missing"; clipping afterwards turned masked cells into -3276.7 m/s. Values are checked against Open-Meteo after any change to the script (wind, cloud, cape agree; 2 m temperature is the raw model value, about 2 to 3 degC warmer than Open-Meteo's elevation-corrected figure in hills).
- Default terrain look (set 2026-11-18, dimmed 2026-11-19): the elevation-colour terrain, NOT satellite imagery. `LAND` in `core.js` is a bright hypsometric palette (green plains to about 650 m, olive then orange-tan hills, grey-brown high ground, white above 4,800 m) and `PLAIN_LIGHT` in `app.js` (sun 2.1, hemisphere 0.834, ratio 2.52) lights it; those two lights are the ONLY lights in the scene, and there is no baked hillshade (the DEM colours are a flat table). The user's targets are plains #546B3D and hills #806147; measured with the wind trails off (headless screenshot of the Islamabad / Margalla view) the plains are #677237 and the hills #675D3C. Lowering the lights cannot close the rest: scaling them keeps each colour's red-to-green ratio, so the plains' remaining yellowness and the hills' missing red are in the `LAND` colour stops. The Satellite imagery checkbox (`t-sat`) is off by default and still switches to imagery with its own light levels. Change the stops and the lights together, never one alone.
- Terrain: base DEM and Esri World Imagery at zoom 7 for the country (1.2 km per pixel). When the camera is close, nested 5 x 5 tile levels are drawn over it at zoom 9 (about 250 m, under 900 km), 10 (130 m, under 320 km) and 11 (65 m, under 110 km), loaded one at a time, coarsest first, after the camera has stopped (`LOD_LEVELS`, `lodWanted` in `core.js`; `checkPatch` in `app.js`). Each level blends into the one below over a border of 8% of its width (`FADE_FRACTION`): the colour alpha fades in over the outer border while the geometry there follows the lower level's heights exactly, then the heights move to the level's own; the lower levels are cut away (shader holes) only inside that border. Draw order: opaque base, detail levels (renderOrder 1 to 3), wind (20), clouds (30). Clouds are an animated shader driven by ECMWF total cloud cover; wind trails are born inside the visible area.
- Wind trails run on the GPU (WebGL2 float render targets; `?cpuwind` forces the old CPU path): 8,192 particles, about 6,000 drawn by default, each a 14-point ribbon draped on the terrain and tapered at the tail; constants in `WIND_SIM` (`core.js`). Speed control has steps 0.5, 1, 2, 4, 6x (`SPEED_STEPS`); positions are recorded per amount of wind time (`slotInterval`), so a trail is the same length on screen at every speed; Trail length (4 to 13 segments) sets `uTrailSegments`. Frame time is clamped to 0.05 s.
- Wind trail look (overhaul): GPU_W x GPU_H = 256 x 96 = 24,576 particles, default 16,000 (`?density=N`, slider 2,000 to 24,000). Ribbons have a dark halo (`RIBBON`, `vSide`). Calm-air fix: each particle keeps one heading per life (hash of its own texel and life), the heading blends along the shortest arc with wind speed (`calmBlend`, `withMinimumSpeed` in `core.js`); never re-randomise the heading per frame (that was the "parasite squiggles" bug). Surface wind of 1 to 3 m/s draws short, pale trails: low contrast on light terrain, not a fault.
- Smooth loading and quality: grid geometry, DEM decode and flow grid run as generators in 5 ms slices (`runSliced`, `gridGeometryJob`, `decodeDemJob`, `flowGridJob`); textures are uploaded over several frames. No resampling in zoom/move handlers. Quality governor (`QUALITY_STEPS`, `newQuality`, `qualityStep`): slow frames (>24 ms) step the pixel ratio and trail draw range down, fast frames (<12.5 ms for 6 s) step up; the EMA sample is clamped to 60 ms so one hitch does not drop quality. `?fps` shows the frame rate and quality notch. 60 FPS is NOT verified on a real GPU.
- Pressure levels: nine levels (Surface, 1000, 925, 850, 700, 600, 500, 400, 300/250 hPa, `PRESSURE_LEVELS`). The sync writes `public/terrain-data/levels/p<level>.json` (+ `index.json`; u, v, t, gh, generated, never committed); `grid-hires.json` now runs to 144 h (49 steps) with a `gust` field (ECMWF `10fg`, only to 90 h). The 1 km layer covers the first 72 h only (`validManifest` accepts a prefix, `with1km` leaves later rows at 9 km). The wind texture alpha holds the level's real height (km); trails are masked where the 1 km terrain is higher than the level (`levelUnderground`, margin 50 m) and drawn at that height. The right-hand altitude bar (`#alt-bar`) lists hPa, standard height in km and ft. Share link suffix `,<level>` for any of the nine levels; hour up to 240 is accepted.
- Forecast drawer (replaces the old point popup): click the map to open the bottom drawer `#fc` (`forecast-ui.js` renders; `forecastTable` and `weatherIcon` in `core.js` compute). Local-time 3-hourly columns, SVG icons, colour-coded temperature, rain bars (blank when dry), wind arrows coloured by gust class, km/h or kt toggle. Reads the loaded grid, no API call. Columns past +72 h are 9 km and drawn lighter. Tests: `test/terrain-explorer-forecast-ui.test.js`, `test/terrain-explorer-levels.test.js`.
- With "Follow the terrain" the surface (10 m) trails use the 1 km mass-consistent wind of `grid-1km` when it is loaded (decoded in the shader, `wind1km`), otherwise the slope rule of `terrainWind`/`flowGrid` (`FLOW` constants; uphill flow into a steep slope turns along the contour, crests faster, valleys slower). Neither has thermal valley or slope winds. All are screening adjustments, not a weather model.
- Labels: `scripts/sync-terrain-labels.py` (standard library only) downloads GeoNames PK.zip (CC BY 4.0) and writes `public/terrain-data/labels-pk.json` (about 23,600 labels, 1 MB): cities and towns by administrative code and population, villages thinned to one per 5 km, peaks and passes by height; tiers 0 to 5, each shown while the camera is closer than `maxDistKm[tier]`. This file is static: commit it, run the script only to refresh it. The page picks candidates by 1 degree cell (`labelIndex`, `labelsNear`), never overlaps labels, and falls back to the portal's 86 cities if the file is missing.
- Layers and controls: Temperature drape (2 m, `l-temp`, letter `t` in the share link) is drawn under rain and snow and is disabled when the grid has no `t2m`. With `grid-1km` loaded, temperature and rain are drawn by the terrain shader from the 1 km step PNGs (`DRAPE_CODE`, colour look-up tables `temperatureLut`/`rainLut` matching the CPU ramps); snow stays on the CPU overlay from the 9 km grid. The title shows a badge "1 km ML downscaled (PMD + ECMWF) · N live stations" with details in its tooltip. Wind altitude selector (10 m, 850 hPa, 700 hPa; link suffix `,850` or `,700`) draws pressure-level trails at about the level's standard-atmosphere height, stops them where the level is underground, and applies the terrain adjustment to the 10 m wind only.
- Click for forecast reads the loaded grid (`pointRows` in `core.js`: hourly rows by linear interpolation in space and time), so it makes no request to a forecast API and the explorer makes no `api.open-meteo.com` call. With `grid-1km` loaded, temperature and rain come from the point's 1 x 1 degree tile (`tileOf`, `tileSeries`, `with1km`; one small PNG request) and the panel says so; wind, CAPE and snow stay 9 km. The source is 3-hourly (rain is a 3-hour mean) and CAPE is most-unstable CAPE, so the 500 J/kg screening rule for convective rain fires a little more often than it did with Open-Meteo's `cape`.
- Attribution shown bottom right: ECMWF Open Data (CC BY 4.0), GeoNames (CC BY 4.0), Esri imagery, AWS Terrain Tiles, three.js (MIT). Tests: `test/terrain-explorer.test.js`, `test/terrain-explorer-layers.test.js`, `test/terrain-explorer-wind.test.js`, `test/terrain-explorer-1km.test.js`. Not yet tested on a real GPU (60 FPS with 6,000 to 8,000 ribbons unverified; headless Chrome renders in software) or with touch.
- Not built on purpose: lightning and station overlays (the user does not want them here), a fronts overlay (no data source).

## 1 km downscaler (`downscaler/`, local only so far)
- Python in `.venv-terrain` (openpyxl, pandas, pyarrow, scipy, rasterio, lightgbm, catboost, scikit-learn, pyamg, earthengine-api). Tests: `.venv-terrain/Scripts/python.exe -m unittest discover -s downscaler/tests`. `downscaler/data/` and `downscaler/models/` are git-ignored (PMD data).
- `1_prepare_and_train.py --source gee --ee-project calude-app` (about 15 min): PMD FFD workbooks on the Desktop (rain `FFD-Monthly Rainfall Statement (2012..2022).xlsx`; temperature `rainfall  2018\FFd Monthly Temperature (2016-2022).xlsx`, MAX and MIN blocks in either order, titles with typos: `pmd_xlsx.py`) plus WeatherWalay Davis exports (`extra_stations.py`: Shimshal (temperature only, gauge unreliable), Murree, Nathia Gali, Chilas; 1- or 15-minute records turned into PMD-style days: max over the PKT day, min and rain over the 24 h to 08:00 PKT, coverage checked in the hours that matter). Positions from realtime.json PMD rows (`stations.py`), Astore and Cherat from `POSITION_OVERRIDES` (confirmed by WeatherWalay), PMD Observatories page only as a height check. ERA5-Land daily from Earth Engine `ECMWF/ERA5_LAND/DAILY_AGGR` (CC BY 4.0 data; Earth Engine itself is non-commercial: switch to Copernicus CDS before a commercial retrain), 1 km Copernicus GLO-90 terrain (`terrain.py`). LightGBM + CatBoost; temperatures as a correction to ERA5-Land, rain as wet-day probability x amount; GroupKFold by station; report by elevation band with a 6.5 degC/km lapse-rate baseline.
- `2_apply_1km_forecast.py` (about 10 min, mostly model prediction; run by the ECMWF sync): 1 km daily max/min and rain pattern on 2.6 million land cells, 3-hourly steps following ECMWF's diurnal shape, rain spread inside each 0.1 degree cell with its water kept exactly, live station nudging (elevation-aware Barnes, fading over 12 h), mass-consistent 10 m wind (`forecast1km.MassConsistentWind`, pyamg; 2D single layer relative to ECMWF's own terrain, speed-up capped at 2x). Writes `public/terrain-data/grid-1km/` (generated, about 180 MB: RGB PNGs, 24-bit packing described in `manifest.json`; never commit). JSON must be written with `json_safe` / `allow_nan=False`: a bare NaN once made the browser reject the manifest.
- Rain / snow split (`downscaler/phase.py`, pure and tested in `downscaler/tests/test_phase.py`): Ding et al. (2014), J. Hydrol. 513, 154-163, equations 7 to 10, 13, 14 and A.2/A.3 transcribed from the accepted manuscript and verified by their defining properties (equal snow and sleet probability at Tmin, equal rain and sleet at Tmax; the dual-threshold crossover at about 78 % humidity). Inputs per 1 km cell and step: wet-bulb temperature from the FINAL 1 km temperature, RH from ECMWF `2t` and `2d` (read by the ECMWF sync as a downscaler-only field) held constant in each 0.1 degree cell, and the cell height (Z; ps is the ICAO standard-atmosphere pressure at that height). Snow if Tw <= Tmin, sleet between (split half and half: our convention), rain if Tw >= Tmax. Written as `steps/ph-NNN.png` and `tiles/ph_<lat>_<lon>.png` (red = round(255 x snow share); the temperature + rain PNGs still hold the TOTAL water); a manifest without `phase` or a cache without `2d` simply has no split and the explorer keeps the 9 km ECMWF snow overlay. In the explorer the terrain shader draws rain and snow as separate layers from the share (`DRAPE_CODE`, `tSnowLut`), and the click forecast uses it through `with1km`. Limits that must stay in the wording: the scheme was fitted to DAILY means at Chinese stations (about 88 % accurate, best on the Tibetan Plateau, not evaluated elsewhere; its authors expect lower thresholds for hourly data) and is applied here to 3-hourly values; there is no solid-precipitation observation to validate against, and unheated tipping-bucket gauges (all Davis stations, Shimshal included) miss snow. The manifest reports agreement with ECMWF's own snowfall and with the Jennings et al. (2018) logistic (cross-check only). Wet bulb is Ding's linearised formula, which differs from exact psychrometry by about 0.7 degC at 20 degC and 50 % humidity.
- Topographic features and decoupled temperature targets (research, NOT in the production models): `downscaler/topo.py` (pure, analytic tests in `tests/test_topo.py`) gives multi-scale TPI (3, 9, 25 km), roughness, relative position, valley depth, a sky view factor from 8 horizons, and `pot_rad_ratio` (daily clear-sky beam radiation on the slope over flat ground, Cooper 1969 declination; varies with the day). The 1 km grid cannot resolve a gorge narrower than about 2 km. `scripts/add_topo_features.py` adds them to a training matrix (cache `downscaler/data/topo_1km.npz`); `features.TOPO_BY_TARGET` gives tmax the sun / shading / convexity set and tmin the cold-air pooling / drainage set (design choices, tested by cross-validation, not published thresholds); `train_downscaler_v2.py --ablation topo --hold Murree` compares them with and without, and reports bias and RMSE of the held-out stations (Murree PMD + WeatherWalay) per variant. The WeatherWalay Murree station is trusted and stays in the production training set (it is held out only inside this experiment); its warm held-out bias (about +3.4 degC tmax) is an open model weakness at ridge-top sites, not a sensor fault. `Predictor` accepts a dict of feature lists per model.
- Regime-dependent live bias (`forecast1km.py`: `classify_regime`, `fit_regime_bias`, `regime_bias`; tested): a clear-calm ("inversion") curve and a windy curve of bias against height, from ECMWF cloud cover and 10 m wind at each station at analysis time (`REGIME` thresholds are screening conventions). Runs in SHADOW MODE: `live_bias_history.csv` now records regime, cloud and wind, the curves are fitted and reported in `manifest.live_bias.regime`, but only `2_apply_1km_forecast.py --regime-bias` applies them (a regime needs 150 residuals from 3 analysis times, else the pooled curve). It could not be validated: the history had no regimes. Review the log line and the curves after about a week before turning it on.
- Kriging of station bias (exploration only, `downscaler/kriging.py`, `scripts/krige_explore.py`): leave-one-station-out of the raw ERA5-Land bias. In the mountains (15 stations) a regression on height leaves 4.8 degC RMSE, ordinary kriging of the raw bias 3.2 (tmax) and 2.1 (tmin); kriging what the regression leaves adds nothing for tmax (pure nugget) and little for tmin. Small, clustered sample; not used by the forecast.
- Known limitation, handled: the models learned ERA5-Land's high-valley cold bias (about -17 degC), but ECMWF IFS has about half of it, so applied to IFS they over-correct in the mountains (+8 degC at 62 live stations on 17 Nov 2026). Two fixes: outside the training stations' range of height and delta_z the correction fades to the lapse rate (`ml_weight`), and a live elevation bias curve fitted to fresh stations (pooled 7 days in `data/live_bias_history.csv`) is removed at every step. Held-out check on 17 Nov 2026 05:58 UTC, mountains: ECMWF MAE 9.5 degC, 1 km 6.4, 1 km + live bias 3.7; plains unchanged (about 1.4). Only one time of day so far; keep watching the check table each run.
- PMD synoptic rows in realtime.json had not synced since 13 Nov 2026, so live checks use the other networks (GLOF, Davis, WU, ...). Screening estimate, not an official PMD forecast.

## Live stations (Maps page, "Live stations" tab; the old airports map is the "Airports (METAR)" tab)
- `public/realtime/` (`index.html`, `app.js`, `core.js`, `palettes.js`) is an iframe page: parameter and category picker as on forecasting.weatherwalay.com/realtime, MapLibre map with values on stations, sortable table, a station detail panel (every parameter and category with its time stamps, then all 178 raw columns) and CSV export. Basic = temperature, humidity, pressure, wind, rainfall, rain rate, solar, UV, visibility; derived = dew point, wet bulb, heat index, wind chill, THW, THSW, hair frizz; "against normal" = normals and departures. Air quality, radar, interpolation and the timeline are deliberately not included.
- Data: `scripts/sync-realtime.mjs` (one login, shares `fetchFeed` with `observation-sync.mjs`) writes `public/observation-data/realtime.json` (all 963 stations, all 178 columns in natural order with labels, feed time), `station-meta.csv` (exact name, network, latitude, longitude, elevation) and `station-elevations.json` (cache). The dev server serves `/observation-data/realtime.json` live; CI publishes it in `observations.yml` and `pages.yml`. Run it locally with `node scripts/sync-realtime.mjs` (login from the git-ignored `.env`; never print it).
- PMD FFD overlay: `scripts/pmd-ffd.mjs` reads ffd.pmd.gov.pk/staff/weather-display (one page per station, `?city=<slug>`, 101 stations; PMD has allowed use, including model training). Observed weather and its time stamp only, never the forecast block. Matched to PMD rows by WMO id, then name; fills temperature, dew point, humidity, pressure, visibility (km to m) and rain since 08:00 PKT with the page's own sync label, clears stale values sharing that stamp, keeps a row whose own sync is newer. Max/min today and yesterday live only in each station's `pmd_ffd` object (no recorded time on the page). Wired into `sync-realtime.mjs` (`PMD_FFD=0` disables; a failure only logs). A full pass takes about 2 min, so the 10-minute CI cadence is untouched. Page positions are 0.1 degree (existing positions kept); about 6 stations have no observation. Tests: `test/pmd-ffd.test.js`.
- Live-reading quality control: `scripts/obs-qc.mjs` (JS, used by `sync-realtime.mjs`) and `scripts/obs_qc.py` (Python twin, used by `sync-metar.py`) read ONE rule file, `scripts/qc-rules.json`, and are tested against the same vectors (`test/fixtures/qc-vectors.json`, run by `test/obs-qc.test.js` and `downscaler/tests/test_obs_qc.py`): change a rule in the JSON and the vectors, never in one language only. Checks: `range` (world records: only impossible values), `dew_above_temperature`, `spatial` (temperature against the median of stations within 40 km, 700 m and 90 min after the 6.5 degC/km lapse correction; needs 3 neighbours), `spike` (jump larger than allowed AND not supported by the neighbours), `stuck` (temperature identical for 6 h). Only the range limits are sourced; every other number is a screening convention calibrated on realtime.json so that about 0.1% of readings are flagged. Flagged readings are NEVER removed: the station / METAR row gets `qc: {parameter: [rules]}`, the file gets a `qc` summary, `qc-report-*.json` lists every flag with its numbers, and `qc-state-*.json` carries the last good value per station and parameter to the next run (CI fetches it from the `data` branch; without it only range, dew and spatial run). `downscaler/2_apply_1km_forecast.py` (`drop_flagged`) sets flagged temperature, wind (speed or direction) and rain to missing, so they enter neither the live bias curve nor the Barnes analysis; the manifest counts them in `assimilation.qc_excluded` and `live_bias.qc_excluded`. `OBS_QC=0` disables it. Not covered: wind and rain neighbourhood tests, stuck tests for humidity, pressure, wind and METAR. METAR rows now carry `elev` (metres, from the API) and the downscaler uses it as the station height.
- SINGLE SOURCE: `realtime.json` is the only source of WeatherWalay stations, sensors and rain gauges for the whole portal. Everything reads it through `public/station-feed.js` (`fetchStationFeed`), which derives the compact station shape in `public/station-records.js` (`slimFromRealtime`): current conditions on the Weather page (and so Health and Farmers, which receive that observation), the Climate and Flood panels, the Airports (METAR) map's station layer, the Live stations page. `stations.json` is no longer fetched separately: `scripts/sync-realtime.mjs` writes it from the same login as a view of `realtime.json`, only for the CI archive (`archive-stations.py`) and the transitional fallback in `fetchStationFeed` (used only while realtime.json is not yet published; remove it afterwards). Station elevations from realtime.json seed the terrain-aware station choice (`seedElevation`). METAR is a separate feed and untouched, and the choice order (fresh representative station, then airport, then ECMWF; terrain rules in `terrain-source.js`) is unchanged.
- The column layout (which column is which value, time or sync) comes from the realtime page's own scripts and lives in `PARAMS` in `core.js`; columns the page never uses stay "unlabelled". Time labels like "11:53 am, 13 November" are PKT with no year: `parseLabel` takes the most recent year that is not in the future. A station is active when its last sync is at most 30 minutes old.
- Feed quirks, kept as given but handled: 181 stations have no id (the key falls back to name and position), one station has latitude and longitude swapped (flagged in `position_note`, corrected only for the map and the elevation lookup), the 90 IMD stations (Indian Kashmir and Ladakh) are in `realtime.json` but not in `stations.json`. Elevation is NOT in the feed: it is the Open-Meteo 90 m terrain model at the position, labelled as such, not a surveyed height.

## Offline use (PWA)
- `public/sw.js` (service worker), `public/pwa.js` (registration, offline banner), `public/manifest.webmanifest`, `public/icons/` (made by `scripts/make-pwa-icons.py`). New root `.js`, the manifest and `icons/` are in the `server.js` allow-list. The worker is registered only on https (GitHub Pages), or on http with `?pwa=1` / `localStorage ww-pwa=1`: on localhost it would serve stale scripts while code is edited, so leave it off during development, and restart `server.js` after editing it (a running server does not reload).
- Policy (`strategyFor` in `sw.js`, tested in `test/pwa.test.js` by running the real file in a `vm` sandbox): pages and our own data directories (`observation-data`, `terrain-data`, ...) NETWORK FIRST with an 8 s limit, so live data is never replaced by a stored copy while online; scripts, styles and images stale-while-revalidate; AWS terrain, Esri imagery and OpenStreetMap tiles cache first, capped at 800 entries; forecast APIs, Google Map Tiles (their terms do not allow storing them), non-GET and range requests are never touched. Only what the person has opened is stored (plus a five-file shell), so offline use means "what you looked at while online"; the 1 km set is stored for the steps that were viewed. Bump `VERSION` in `sw.js` to drop every stored copy. The banner in `pwa.js` says forecasts and station readings may be old when the device is offline.
- Open: Esri and OpenStreetMap tile terms for on-device caching were not checked (only tiles the person viewed are kept, capped); nothing is downloaded ahead of time for a trip, so an explicit "save this area" step would be a separate feature.

## Weather page source choice and forecast
- `public/terrain-source.js`: hills-aware choice (a station/airport must match the place in height: plain 200 m, hilly 150 m, mountainous 100 m, wider within 3 km, with shorter distances). Constants are screening conventions, marked as such. The ECMWF forecast is shown unadjusted (a station-based adjustment was tried and removed on request).
- `public/hail.js` (own ingredient index from ECMWF CAPE, 0-500 hPa wind change, T500, convective rain; not a probability) and `public/forecast-periods.js` (day = sunrise to sunset, night = sunset to next sunrise; icon, rain, snow, hail per half).

- ECMWF (via Open-Meteo) gives no thunder weather codes and its `showers` field is always 0, so thunder and hail use CAPE plus rain (`storms.js` `thunderEvidence`, `hail.js`). `public/lightning-nearby.js` adds observed strikes within 25 km in the last hour from the live Lightning buffer; it marks the current half-day only, never the forecast.
